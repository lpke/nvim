This is my neovim configuration repository.

- When adding keymaps, always prefer to use `keymap_set` (single), `keymap_set_multi` (multiple), `ft_keymap_set_multi` (filetype specific), or `telescope_keymap_set_multi` (telescope pickers) helpers from `lua/lpke/core/helpers/config.lua` over the native neovim keymap setting functions unless they dont fit the requirement.
- Always consult `lua/lpke/core/helpers/` and `lua/lpke/core/globals/` to check if any helper functions exist for the required task before writing code from scrach
- Remember to consult relevant plugin source code when making changes that involve plugins (~/.local/share/nvim/lazy/...).
  - `lua/lpke/local_plugins_src` contains the source code for plugins I've chosen to contain locally rather than install through Lazy. They are still initiated with Lazy under `lua/lpke/plugins/<plugin>.lua`
- Keep the custom CodeCompanion `g?` extension in `lua/lpke/plugins/ai/helpers/keymap_help.lua` in sync when user-facing chat commands, keymaps, or workflows change. Apply the same help maintenance rules as `doc/lpke-help.txt`, including the Syslore update below.
- When adding LuaSnip snippets with `fmt`/`fmta`, remember literal `>` characters (for example in JS arrows `=>`) conflict with the `<>` placeholder delimiter unless escaped or avoided. Use plain nodes or a different formatter delimiter when the snippet body contains literal `>`.
- Keep `doc/lpke-help.txt` as a concise reference for user-facing custom commands, keymaps, workflows, snippets, and filetype behavior worth looking up later. Update it when those features change, not for every plugin, script, or configuration edit. Use the `syslore` skill, if available, to keep the relevant Syslore records up to date alongside the help.
- Each help entry should show an invocation, shortcut, or snippet trigger and a short description. Keep only context needed to use it, such as modes, scope, or cancellation rules. Link to existing command/plugin help or pickers for detailed options. Keep internal Lua APIs, storage paths, dependency/version inventories, machine-specific identifiers, troubleshooting, maintenance instructions, and fix history in source comments or repository documentation instead.
- Keep `doc/tags` in sync with `:helptags doc` when help docs change.
